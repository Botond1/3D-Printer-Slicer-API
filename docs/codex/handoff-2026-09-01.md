# Handoff — 2026-09-01

Written for whoever picks this repository up next. It is deliberately short on
history and long on the things that will bite you.

## Where the service stands

`main` is the only branch. Everything else was merged and the branches deleted on
2026-09-01, so if something is not on `main` it does not exist.

Production runs the signed candidate for `main`, deployed and verified end to end.
The public route `api.rocket3d.hu` is **live**, behind two allowlist layers, admitting
exactly one partner address. Both consumers — the WooCommerce plugin and LeadPilot —
are integrated in contract but **neither is switched on**, so there is currently no
customer traffic. That makes this the cheapest possible moment for anything risky.

## What changed most recently, and why it matters

Quotes through the two engines disagreed by **7.7x** on print time, and therefore on
price. The cause was ours and is now fixed:

- `filament_max_volumetric_speed` was inheriting **2 mm³/s**, OrcaSlicer's default for a
  **0.2 mm nozzle**, throttling every Orca quote. Now 12 on both engines.
- Only the 0.2 mm Prusa profile had ever been configured for this machine. The 0.1 mm
  and 0.3 mm profiles carried MK3-class speeds an order of magnitude slower, so the same
  model was quoted several times higher purely by choosing a different layer height.
- The Prusa route reported no mass and therefore no price at all; every FDM quote fell
  through to manual pricing. It now receives a per-material density.

Result: time divergence **7.7x → 1.04–1.48x**, material agreement within ~2%.

The full attribution, including the three hypotheses that were tested and falsified, is
in `docs/research/calibration-protocol.md` (gitignored, local only).

## Traps that have already cost time

**The vendored Orca `Custom` parent profiles are byte-pinned.** A build-time gate
(`scripts/verify-orca-profile-vendor.js`) requires `fdm_machine_common`,
`fdm_process_common` and `fdm_process_marlin_common` to stay byte-identical to the
OrcaSlicer bundle. Every profile override must live in our own leaf profiles under
`configs/orca/`. Editing a parent looks tidier and breaks the image build.

**The operator pack must be a git working checkout, not a tarball.** The operator
contract runs `git rev-parse --show-toplevel`; an extracted archive fails with
`operator_pack_file_invalid` and no further explanation.

**Node must be installed on the VPS itself, not run in a container.** Every router
helper verifies an inherited FD 9 flock, and a container cannot inherit a host file
descriptor. Running the helpers in a container would bypass the concurrency guard the
lock exists for. `node:20-bookworm` has both node and git; the `-slim` variant has no git.

**A fresh clone never satisfies the mode contract.** Git does not preserve non-executable
modes, so after cloning, `ops/hostinger/dynamic` is 755 and `.gitkeep` is 644 while the
contract demands 0700 and 0600, and `.runtime-private/{staging,rollback}` plus the lock
file do not exist at all.

**`docker compose` must be given `-p slicer-api` explicitly.** It otherwise derives the
project name from the working directory, which changes per release, and the deploy fails
on a container name collision. It fails safely, but it fails.

**`--dport 443` matches nothing in `DOCKER-USER`.** That chain runs after Docker's DNAT.
The perimeter rules use conntrack original-destination matching instead. A plain port
rule would look correct and protect nothing.

**IPv6 does not traverse `DOCKER-USER` at all** on this host, because there is no IPv6
DNAT — it arrives as host `INPUT`. An IPv4-only rule leaves the whole TLS surface exposed
over IPv6.

**MSYS mangles `git` refs containing a colon or a path.** `git show "origin/main:file"`
and `git cat-file -e "origin/main:file"` silently misbehave from Git Bash on Windows
unless prefixed with `MSYS_NO_PATHCONV=1`. This produced one false "file missing from
main" finding before it was caught.

## Hard rules

- **Never push `claude/sz-b2-orca-headless`.** It still exists as a local branch and
  contains real customer names, lead IDs and order numbers. **This repository is public.**
  The useful part of it was extracted and anonymised long ago into
  `docs/kalibracio-2026-08.md` as `M01`…`M10`.
- **Never commit a real IP address, hostname or credential.** Every PR is scanned for it;
  the documentation uses RFC 5737 ranges (`192.0.2.0/24`, `198.51.100.0/24`,
  `203.0.113.0/24`) and `.invalid` hostnames deliberately.
- **Route activation, DNS changes and allowlist changes need direct owner approval**, and
  the runbook additionally requires separate authorization before stopping the running
  Traefik.
- **DNS for the API name must stay grey-cloud (DNS only).** Proxying it would make every
  request arrive from the CDN's ranges and the IP allowlist would become meaningless.

## What is open

**Calibration phase 2 — a physical print.** After every measurable configuration
difference was corrected, a **1.04–1.48x** time difference remains between the two
engines, and it is *not* a constant: it varies with geometry. That is the two slicers'
time estimators disagreeing, and no configuration change closes it. A scalar correction
factor is ruled out empirically. Only wall-clock on the real machine can say which
estimator is right. **Do not print our own G-code** — it is generated against a generic
Marlin identity and the printer runs Bambu firmware. Slice the same models in Bambu
Studio with the official P1S profile and print those.

**H2D has no real profile.** The `350 x 320 x 325` envelope is served by a P1S-derived
*quoting* profile: P1S physics on an H2D-sized bed. The estimate is conservative and the
G-code is quote-only, never printable on that machine. Its start G-code says so. A real
profile needs hardware measurement.

**SLA is PrusaSlicer-only** and emits SL1. The actual printer is an Elegoo Saturn 4 Ultra,
which is a different machine class and format. That path has never been exercised.

**The infill pattern cannot be aligned** between engines: PrusaSlicer rejects
`crosshatch`. Verified by invocation. This is a genuine incompatibility, not a defect.

## How to verify anything

Never trust a local test run alone for behaviour that depends on the slicer binaries.
Build the image on the VPS and exercise it in a container with the production isolation
envelope, then compare against the recorded baselines. The pattern used throughout:

1. `git archive` the commit, ship it, `docker build` on the VPS.
2. Run with `--read-only --user 999:999 --cap-drop ALL`, tmpfs `/tmp` at
   `uid=999,gid=999,mode=0700`, 4 GiB / 2 CPU / 512 pids, no published ports.
3. Drive it over HTTP from a disposable peer on the `slicer-api-private` network.

Regression baselines worth keeping honest, all measured on the current build:

| Check | Expected |
| --- | --- |
| Orca X/Y envelope | 253.9 passes, 254.0 returns 422 |
| Z envelope, both engines | 249.9 passes, 250.0 returns 422 |
| H2D-QUOTE | Prusa 350x320, Orca 347.9x317.9, Z 324.9 |
| Zero-normal mesh | 200 with `original_dimensions_available: false`, never 500 |
| 40 mm cube, PLA | Prusa 1980 s / 24.7 g / 450 Ft; Orca 2760 s / 24.2 g / 620 Ft |
| PETG vs PLA mass | ratio must equal 1.27 / 1.24, proving per-material density |
| G-code footprint of a 249x100 body | X span ≈ 248.6, Y span ≈ 99.6 — proves no hidden yaw |
